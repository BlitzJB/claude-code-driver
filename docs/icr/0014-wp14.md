# ICR 0014 (WP-14): testing-kit conventions other packages rely on

- **Status:** accepted (2026-11-03, WP-14). No change to `src/model/**` or `src/platform/ports.ts`.
- **Files:** `src/testing/**`, `scripts/fixtures-{from-verify,scrub,lint}.mjs`, `fixtures/traces/**`, `test/kernel/**`.

1. **How `createTestKernel` reaches L3 (WP-11, WP-12, WP-13).** `src/testing/test-kernel.ts` loads the session entry points at run
   time, so the kit type-checks before they exist. It expects:
   - `src/session/config.ts` exports `resolveConfig(spec: SessionSpec, env: EnvPort, defaults?)` returning `ResolvedConfig` (sync or
     async) and, optionally, `DEFAULTS` (passed back as the third argument);
   - `src/session/kernel.ts` exports `createSessionKernel(ports: Ports, config: ResolvedConfig)` returning a `SessionKernel` (sync or
     async). If the returned object also has a `start(): Promise<unknown>`, the kit awaits it (the runtime's `createKernel` resolves at
     ready); otherwise it waits with `waitFor(lifecycle ∈ {ready, gated, exited})`.
   - The kit subscribes with `{ fromSeq: 0 }` right after creation, so events published during start must be in the ring.
   A different shape only needs a new adapter in `loadSessionModules` (or a test passing `modules`); scenarios do not change.
2. **Acceptance gating of K-01…K-52.** `test/kernel/support.ts kscenario(id, wps, …)` runs a scenario as a normal `it` once every
   WP in its brackets plus the kernel base (06, 07, 09, 11, 12, 13) has landed, judged by the sentinel files listed there (each WP's
   entry modules from §1.2). Before that there are two states (verifier change): while `src/session/kernel.ts` or
   `src/session/config.ts` is missing, the scenario is a normal `it` that asserts it fails with exactly `SessionNotLanded` (so a bug
   in the scenario's own code cannot hide behind `it.fails`; `expectStartFailure` rethrows `SessionNotLanded` for the same reason);
   once the session entry exists but a bracketed WP is still missing, it is `it.fails`. A landed WP therefore turns its scenarios
   into real assertions without anyone editing WP-14's files. `CCD_KERNEL_STRICT=1` forces every scenario to `it`.
3. **The scenario world.** `testing/fake-claude.ts` reads the launcher's argv (`--session-id`/`--resume`, `--settings`,
   `--permission-mode`, `--model`) and the settings file the launcher wrote through `SettingsFilePort`; hooks are delivered only for
   registered events, on the registered transport (`http` → http, `command` → unix). The world needs `VISUAL` in the pane env to end
   in `ccd-editor` for C-g to run the FakeEditor injector. Its pane pid is registered in `FakeProcess` with the argv as command
   (identity check of §3.1 step 12). `FakeOwnerWatch` reads `watch.json` from the settings-file port or the state store
   (`FakePortSet.readWritten`).
4. **Fixtures.** `fixtures/traces/*.ccd.jsonl` (15 traces, §6.6 list) were built by `scripts/fixtures-from-verify.mjs` from
   `fixtures/verify` plus the BRIEF hookprobe and faultproxy dirs, scrubbed and linted. All carry `tz: 'Asia/Kolkata'` (the recording
   machine's zone) and `coreInit.config` = `fixtures/traces/core-config.default.json` (= `DEFAULT_TEST_CORE_CONFIG`, kept equal by a
   unit test). They hold `raw` records only, so they replay at the raw level (`replayRaw`). `replayRaw` runs the kernel with the
   header's `tz` and `hookTransport` and `selfTest:'off'`; a record whose fake port does not exist yet is held and delivered, in order
   within its channel, once the port appears (records never delivered come back as `replay.undelivered` diagnostics); it rejects
   at once if the kernel cannot be created, returns `startError` if a created kernel failed to start (a recorded startup gate), and
   refuses `redaction:'meta'` traces. `fixtures/goldens/**` is produced by
   `pnpm test:replay -u` once core and session exist (WP-INT owns `test/replay/**`); WP-14 ships the golden writer/comparer
   (`compareGolden`), not golden content.
5. **Scrub fakes.** The scrubber replaces long hex runs with `cafe0…<n>` and long base64 runs with `FAKEb64x…<nnnn>`. The lint
   allowlist accepts exactly those forms. Recorders that run the scrub rules (the limit recorder, §3.9) should import
   `scripts/fixtures-scrub.mjs` `createScrubber()` or reproduce the same forms, so their output passes `pnpm fixtures:lint`.
6. **Fixture lint contract (verifier change).** `pnpm fixtures:lint` with no arguments lints every committed fixture under
   `fixtures/` (traces, goldens, the scrubbed screen corpus and its labels); the directory walk skips only `fixtures/verify/` and
   `fixtures/raw/`, a file named on the command line is always linted, and a missing path is a finding. JSON lines are checked string
   by string after decoding. The scrubber's replacements never trip a lint rule (`ANTHROPIC_KEY_REDACTED`, `GITHUB_TOKEN_REDACTED`,
   `AWS_KEY_REDACTED`, `[PRIVATE KEY REDACTED]` also for blocks cut by truncation, `Proxy-Auth-Header`/`X-Ccd-Header` for the
   forbidden header names, auth scheme and credential both removed), and its rules run to a fixed point; a fast-check property in
   `test/unit/testing/fixture-scripts.test.ts` asserts scrub output always lints clean.
