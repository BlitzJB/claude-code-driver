# ICR 0011 (WP-11): L3 kernel loop, queue, scheduler, trace, config, self-test cache, limit recorder

- **Status:** accepted (2026-11-03, WP-11). **No change to `src/model/**` or `src/platform/ports.ts`.**
- **Files:** `src/session/{kernel,config,errors-map,queue,loop,scheduler,event-log,redact,debug-trace,selftest-cache,limit-recorder}.ts`,
  `test/unit/session/{config,queue,loop,scheduler,redact,errors-map,selftest-cache,limit-recorder,debug-trace,kernel}.test.ts`.

1. **Kernel ↔ WP-12/WP-13 contract (`session/kernel.ts`).** DESIGN §2.10 fixes the public `SessionKernel` port but not the
   L3-internal seam. WP-11 defines it in `kernel.ts`:
   - `createSessionKernel(ports, config, o?: { services?, step?, lagMonitor?, traceFs? })` returns the kernel plus `start()`
     (resolves at `session.ready`, rejects with the start error; the testing kit awaits it, ICR 0014 item 1).
   - `KernelServices.launch(host: KernelHost, req: LaunchRequest) → LaunchedSession` (`info`, `execute(intent)`,
     `viewCommand()`, `captureScreen()`, `close(o)`, `abort(reason)`).
   - `defaultKernelServices()` is the default composition: WP-12 `launchSession` + `SessionLifecycle` with the WP-13 input
     executor, permission broker, pollers, tail driver and path resolver. Intent routing (one owner per kind, L-2):
     `input` → input executor; `screen.captureNow`/`poll.cadence`/`auth.poll` → pollers; `hook.*`/`host.*` → broker;
     `permission.resolvePaths` → path resolver; `tail.*` → tail driver; `registry.persist`/`process.signal`/
     `lifecycle.finalize` → lifecycle; `net.fault` → sidecar. Every execution is traced as an `effect` record.
   - Close: the core drives §3.8 steps 1–3 itself (`session.close` → deny held permissions → `/exit` job or SIGTERM); the
     kernel waits up to `graceMs` for `process.exited`, then calls `SessionLifecycle.close` with `canExitGracefully: false`
     (never a second `/exit`) and a 1 ms grace when the pane is still alive (escalation only), then tears the loop down.
2. **L1 ingestion lives in the kernel.** `KernelHost.ingestHook/ingestTail/ingestTunnel/ingestCapture/ingestRegistry` record
   the raw L0 record (trace `raw` with `rawRef` on the produced observations, screen ring, limit ring) before normalizing.
   Executors that drive a channel themselves get the *recording* channels through `host.channels.screen` (pollers' `screen`
   option) and `host.channels.transcript` (tail driver's `normalizer` option), so captures and tail lines are recorded too.
   Launch warnings (`LaunchSinks.warning`) are published as `warning` events.
3. **L3-originated warnings without a model change.** `E_LISTENER_THREW` (K-23) and `warning{reason:'limitCaptured'}` (§3.9)
   are published by `loop.publishLocal`: seq = the core's next event seq, folded with `evolve` (so I1 still holds), appended to
   the ring and fanned out like core events. A `host.warning` observation was not added.
4. **Self-test cache scoping.** In-memory entries are keyed per `StateStorePort` instance (WeakMap), not on `globalThis`:
   independent state dirs (and independent test worlds) never share a pass. "Once per library process" is enforced by the pid
   stored in each disk entry; a second package copy of the same process sees the pass through the disk file. The HTTP-failure
   entry is honoured by every process for 24 h (`httpSelfTestFailedRecently`, used by the launcher's `auto` rule).
5. **K-37 relaunch evidence.** Besides the core's `transcriptEvidence`, the kernel watches for a `prompt.recorded` carrying the
   armed nonce and waits up to 1.5 s (fake-clock time) for it after an HTTP ack failure (the transcript lags hooks, P-TAIL-37).
   The relaunch builds a fresh core that continues the event and intent counters, so the published stream stays strictly
   increasing; the failed attempt's `warning E_SELFTEST_FAILED` and `session.exited{startupFailed}` stay in the stream.
6. **Start errors.** Gate → `E_TRUST_REQUIRED` (trust), `E_SESSION_ID_IN_USE`, `E_CONFIG_CORRUPT`, `E_SETTINGS_INVALID`, else
   `E_STARTUP_GATE{gate,text}` (K-04 expects `login`/`apiKey` gates as `E_STARTUP_GATE`). A pane that dies before ready: the
   last startup warning's code (`E_STARTUP_TIMEOUT`, `E_SELFTEST_FAILED`, …), else the final screen matched against the profile
   `startupGates` (`sessionInUse`/`settingsError`/`configError`), else `E_STARTUP_EXITED{exitStatus, finalScreen}`.
7. **Config.** `resolveConfig(spec, env, defaults = DEFAULTS, ids?)` is async only for `realpath(cwd)`; `resolveConfigPure` is
   the pure core. `extraArgs` is checked by the ONE §3.3 allowlist, `argv-builder.ts validateExtraArgs` (pure): no C0/C1
   control character in any value, the recorded `--help` gate (`*-file` flags stay refused while 2.1.316 does not list
   them), `-n`/`-nfoo` forms, reasons in `details.reason`. config.ts keeps the caller's elements unchanged (preflight
   re-validates them; the canonical form of `--name=--x` would not). The lstat checks of `*-file` values stay in preflight
   (I/O). The dangerous-mode list is argv-builder's too. `DEFAULTS` derives the whole `CoreConfig`; a unit test asserts it
   equals `testing/core-config.ts DEFAULT_TEST_CORE_CONFIG`.
   (Verifier fix: config.ts previously had its own, weaker copy of the allowlist that accepted newlines in prompt values
   and `--system-prompt-file`, so a config could resolve and then fail the same check in preflight.)
8. **Host-sleep check before every enqueue (L-4).** Besides every re-arm and timer fire, the kernel runs the scheduler's
   Δwall − Δmono check before it enqueues any non-clock observation, so the first observation after a wake (a screen poll,
   a hook) is preceded by `clock.hostResumed` in seq order (P-API-21, P-NET-42).
9. **Closed loop.** Observations that arrive after `close()` are stamped and discarded, never queued (P-API-09).

## For other owners

- **WP-14 (`testing/test-kernel.ts`):** `createTestKernel` pumps fake time (70 s budget ≈ 7 000 setImmediate turns) while
  `loadSessionModules()` is still importing the L3 graph in real time. The first scenario of a file (and, under parallel
  workers, sometimes the second) exhausts the budget before the kernel even exists → "promise still pending after 70000 ms".
  Fix: `await loadSessionModules()` before entering `pump(started)`. Seen on K-01, K-02, K-06, K-09, K-13, K-17, K-20.
- **WP-09:** K-21/K-19/K-51 fail in the core, not the scheduler: after `hostResumed` the screen claim `usageLimit` with the
  time-only form "resets 3pm" replaces the hook/transcript `resetsAtWall` (rank screen < hook) and re-arms the wake to 3 pm;
  K-51 sees `usage.limited.resetsAtWall` undefined. The scheduler fires `clock.hostResumed` and the ≤ 30 s wall re-checks as
  specified (unit-tested).
